session.applyCompaction · 数据流

status: draft · 设计稿 · 会话数据契约 · 规划出处：能力清单审查 N4 · 权限 session.compact.write（新增） · 尚无 SDK 实现

1接口约定

pi.session.applyCompaction(input: { sessionId: string; summary: string; retainedMessageIds?: string[]; reason?: string }): Promise<PluginApplyCompactionResult>

把插件算好的压缩摘要交宿主托管写回。权限 session.compact.write（新增 · high · 装时确认 · 操作界面可见）。

入参

字段类型必填说明
sessionIdstring是目标会话。
summarystring是非空纯文本；不允许 HTML；超长按 LIMIT_EXCEEDED 拒绝。
retainedMessageIdsstring[]否保留原消息的 id 列表；缺省 = 只留摘要。必须全部属于本会话。
reasonstring否审计标签，如 "diy-summarizer"；随压缩记录落库展示。

出参

字段类型说明
compactionIdstring新建压缩记录的 id。
tokensBeforenumber压缩前工作集 token 估算。
tokensAfternumber压缩后 token 估算。
appliedAtnumber应用时间戳（毫秒）；审计与排序用。

输入样例

{
  "sessionId": "s_01J8",
  "summary": "讨论了存储层三个方案，结论：沿用 SQLite + 压缩检查点；待办：评估 WAL 调优。",
  "retainedMessageIds": ["m_3"],
  "reason": "diy-summarizer"
}

输出样例

{
  "compactionId": "c_01J9",
  "tokensBefore": 48210,
  "tokensAfter": 6120,
  "appliedAt": 1771234567890
}
一句话边界。插件永远不直接改消息列表；宿主托管写回、进压缩记录、界面可见、带来源戳——不是静默改写。Promise resolve 即已生效（下一请求可见）。

2数据怎么走

  1. 提交。插件传 { sessionId, summary, retainedMessageIds?, reason? }。
  2. 校验。主进程校验 session.compact.write 权限；校验 summary 非空纯文本、retained ids 全部属于本会话。
  3. 写入。挂宿主现有 session.appendCompaction RPC：形状校验、按 id 去重、落压缩记录；主进程注入 pluginId 作来源戳（记录「由插件 X 压缩」）。
  4. 可见。界面显示压缩行（renderer 已按 compaction 记录渲染）；审计可查。
  5. 生效。下一请求重建上下文时，摘要 + 保留尾部进入 LLM 视野。
方向内容
插件 → 宿主压缩提交（summary、保留列表、审计标签）。
宿主 → 存储压缩记录落库（CompactionRecord）。
宿主 → 插件应用结果（compactionId、前后 token、时间戳）。

3出错怎么办

情况结果码
未声明 session.compact.writePromise 拒绝，不静默PERMISSION_DENIED
sessionId 不存在 / 已删Promise 拒绝NOT_FOUND
summary 为空 / retained ids 含非本会话消息Promise 拒绝INVALID_ARGUMENT
与宿主并发压缩冲突Promise 拒绝；重读（session.getContext 取新 compactionCursor）再写CONFLICT
summary 超长 / 保留条数超上限Promise 拒绝LIMIT_EXCEEDED

4不提供什么

不给为什么
replaceMessages / 静默覆盖产品已排除；写回必须进压缩记录、界面可见、可审计
消息删除 / 编辑本接口只做「摘要 + 保留」，不动任何消息行
撤销 / 回滚v1 不做；压缩行可见可审计，回滚留后续版本
HTML / 富文本 summary只收纯文本，防注入与界面样式混乱

6还没定的事

summary 长度上限的数值；retained ids 数量上限；压缩结果是否向插件广播事件（普通插件今天收不到任何压缩通知，需另架桥）。
